# 概念原理示意图：让读者看懂产品和使用过程

先确定读者看完图需要理解什么，再选表现方式。概念原理示意图可以包含带标注的产品外形、使用场景、交互分镜、流程图、系统架构图；可以是一张图，也可以是一组。它不是某一种固定画法。

## 按解释任务选图

| 最需要解释的内容 | 优先尝试的表达 | 检查点 |
| --- | --- | --- |
| 装置形态、佩戴或放置、手从哪里操作 | 带标注的外形概念图，配实际使用场景 | 看得见产品、手的动作、按键／接口及关键元件的位置 |
| 多人配合或先后几步才发生效果 | 连续分镜或漫画，必要时加产品局部放大 | 谁发起、谁响应、场景怎样变化、结果是什么 |
| 传感器、主控、软件与反馈之间的关系 | 产品概念图与架构／连接图组合 | 外部可见部件与内部功能一一对应；区分无线、线缆和动作箭头 |
| 条件判断、异常与状态变化 | 流程图或状态图，可与场景／界面组合 | 箭头含义、分支条件、无输入／无法判断时的行为可理解 |
| 纯软件产品 | 关键界面概念和操作场景／界面序列，按需补流程 | 看得见点哪里、输入什么、怎样确认与纠正；不硬加电子元件 |
| 简单机械辅助件 | 外形、接触部位、手部动作与受力方向 | 不为凑架构而虚构传感器、主控或 AI |

这些是选择起点，不是互斥分类，也不要求每项项目画齐所有图。流程图是一种有效可视化；当它已能清楚说明对象与操作时可以采用。当读者仍不知道设备长什么样、手放在哪里或怎样佩戴，就补外形、场景或局部视图。反过来，外形图说不清条件和响应时，补简短流程或状态变化。

## 图中要有的具体内容

硬件项目让关键元件标注指向真实位置；内置元件可用剖视小窗、虚线轮廓或放大图，避免让读者误以为外壳透明。软件项目标注关键控件与输入输出。场景中的人物只画解释操作所需的动作，不将病名转换成刻板身体外观。

先看当前项目已经确定什么，再画什么。尺寸、型号、连接方式或功能未确定时，不凭空画出精确规格；把待选型、草案状态和验证边界写到需求书正文或页面说明。概念图上不加“概念示意·功能与形态待验证”等通用页脚小字，保留有助于理解产品、部件、交互和必要判断关系的标注。概念效果、课堂模拟和已完成实物仍须区分；生成图不是成品照片，也不是患者使用证据。

给绘图工具的说明应包含：核心使用场景、产品形态、交互动作、关键部件和指向关系、可见反馈、需要补充的流程，以及实际放置区域。生成后核对位置、箭头和文字是否正确；错误标注必须修正，不能仅在正文解释。

## 放在哪里，决定怎样取舍

- **需求书／开题书：** 右边约一半区域是一张图或组图，左边为项目背景、现状分析、核心目标、核心功能、实验测试。优先让缩小后的产品和操作仍可辨认；详细参数、技术解释移到补充文字。手机可上下排。
- **PPT／HTML 路演：** 概念图可以独占一页；用大产品图、少量标注和短交互过程帮助学生讲方案。不因此强制新增技术原理页，也不把需求书整页缩进路演。
- **多项目评审 HTML：** 可在每个 idea 标签页顶部放需求书，下方展开开发范围、测试计划、来源与反馈问题。需要转发一个文件时检查图像依赖是否随文件可用。

## 用理解结果验收

遮住长篇说明，查看读者是否仍能回答：给谁用、在什么场景、产品长什么样、怎样操作、得到什么反馈。再检查标注是否准确、关键组成是否可见、图上功能是否在需求范围内。未能回答时补最缺的一种视图，别单纯加更多装饰或更复杂的框图。

方法参考：[IDEO Design Kit · Storyboard](https://www.designkit.org/methods/storyboard.html) 用关键分镜呈现使用者、场景与过程；[Digital.gov · User interactions](https://digital.gov/guides/research-collaboration/designing/user-interaction) 用带场景标注的交互序列讨论方案。只借鉴按理解任务选择视图的原则，不将外部步骤或时长设成课堂强制要求。
