# 项目设计：把想法连成一条可验证的逻辑

学生先描述想法。先用一两句复述“想帮助谁、在什么情境下做什么”，然后只追问当前最缺的环节。默认经过简单几轮讨论就形成草案；不是必须问满几轮。学生要求直接生成，或很难完整表达时，主动补一个可讨论的方案，把假设标清，交老师审核。

## 怎样判断方案是否成立

从真实或明确标为假设的生活场景出发，识别一个具体困难。再看现有办法已经解决了什么、在什么条件下仍不方便。核心目标应回应这个不足，功能应有助于达成目标，测试应能观察目标有没有改善。

例如，“希望拿取物品时少按几次按钮”比“做一个万能 AI 助手”更容易讨论和验证。这个例子只是表达粒度，不是所有疾病都该做同一种产品。

学生只选了疾病时，先结合疾病调研探讨少量具体场景，让学生选择最有兴趣且课堂可做的方向；不要直接从病名跳到“智能手环”。只有困难、使用者、现有办法和可做范围能连起来，才继续收敛功能。如果反复探讨仍找不到合理切入点，坦诚说“这个方向暂时没有想出符合逻辑、课堂能做的方案，可以换一个场景或主题”。不要为了完成模板虚构需求。

## 开题书固定五个板块

| 左侧板块 | 需要讲清楚的事 |
| --- | --- |
| 项目背景 | 问题在哪里发现、如何形成；在目标人群或场景中是否常见。来源不确定就标为待验证的观察。 |
| 现状分析 | 现有解决办法能帮到什么程度、在选定场景中还缺什么；不以“市场上没有”代替检索。 |
| 核心目标 | 用一句话写“帮助谁，在什么场景下，改善哪一个具体困难”。 |
| 核心功能 | 选择足够支撑目标的少量功能；每项都能解释为什么需要。开发范围考虑学生、课时和手头材料。 |
| 实验测试 | 设计 1–2 个简单模拟测试：条件、操作、观察什么、怎样初步判断有效。能够比较有／无方案或改前／改后；属于计划，不填假结果。 |

模拟测试优先使用普通道具、软件任务、计时计数或成人监督下的安全操作。不要让学生通过晒伤、限制呼吸、诱发发作等方式模拟疾病；不要求真实患者参加才能完成开题。

## 交付与概念图

默认交付 **一页可编辑 PPT**：左边五个板块，右边一张概念图。文字用真实文本框，概念图独立可替换，不能把整页截图嵌入 PPT 冒充可编辑。概念图标注主要组成和使用关系，解释方案怎样帮到核心目标，别只画一个漂亮外壳。

- 开题书保存到 `01_需求书/项目开题书_V01.pptx`（已有版本按实际递增）。
- 概念图单独保存到 `02_图纸/概念图/`，标明是方案示意；使用当前平台可用绘图能力或清晰的可编辑结构图。
- 使用宿主现有 PPT／图像能力。没有相应能力时，交付排好五个板块的内容与概念图说明，并明确“待生成 PPT／概念图”，不另造一套渲染工具作为必备依赖。
- 不强制再生产一份内容重复的 Word／Markdown 需求书。有短项目说明时更新目标、关键功能和文件链接，方便 ChatMaker 接续。
- 输出前检查五块之间是否相互支持、字是否可读、是否真的一页、PPT 文字是否可编辑、概念图是否单独存在。标明“草案，待老师审核”，除非老师已经明确审核通过。

老师或学生改变目标时回头检查功能和测试是否一起变化，不能只改标题。
