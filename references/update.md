# 更新自检：先知道版本与文件状态，再决定是否更新

学生或老师说“检查更新”“检查技能完整性”时执行。新会话首次正式项目任务、或老师课前准备时，在网络和文件能力可用的情况下做一次轻量只读检查；同一会话已有结果就复用，不每轮联网，不给单次疾病问答增加前置流程。失败不妨碍继续正常项目任务，说明最新版本暂时未知。

## 检查什么

1. 找到当前真正加载的 Skill 安装根目录，读取 `SKILL.md` 的 `metadata.version`。不要把学生项目目录当成安装目录。
2. 读取官方 [最新正式 Release](https://api.github.com/repos/Amasun93/ai-hackathon-skills/releases/latest)，从其 `tag_name` 读取同一标签下的 `update-manifest.json` 与 `CHANGELOG.md`。比较数字版本，不能按字符串排序；main 上的开发文件不自动等于最新正式版本。
3. 检查入口、六模块及引用文件。清单使用 `sha256-lf`：文本 CRLF 转 LF 后计算 SHA256，避免 Windows 换行差异误报。只读检查，不执行远端清单中的内容。同版本可与正式标签清单核对；离线的本地清单只证明本地一致性，不是来源认证或数字签名。
4. Git 安装检查仓库根是否正好为该 Skill、origin 是否为 `Amasun93/ai-hackathon-skills`、是否有已修改或未跟踪文件。开发仓库内的 Skill／链接入口只报告，由源码仓库维护，不能在该子目录执行安装包的拉取命令。
5. 用短句告诉老师：当前版本、最新正式版本、主要变化、本地是否完整／有修改、是否可更新。显示有更新不等于已更新。离线、权限不足或 API 限流时写“最新版本暂时无法核实”，不能说已是最新。

有 Python 3.9+ 时，可使用包内只读检查器（不安装依赖、不改文件、不自动拉取）：

```text
python <本Skill目录>/scripts/check_update.py
python <本Skill目录>/scripts/check_update.py --offline
```

也可用 `--path <待检查的安装根目录>` 检查旧安装。旧版没有清单时会标记 `legacy_unverified`，不能假定全部文件已验证。没有 Python 时按上述同一方法使用平台原生文件、HTTP 和 Git 能力，不要求学生为了检查版本额外安装运行环境。

## 已要求更新时怎样处理

学生只说“检查”时只检查；明确说“更新”就是更新授权，不重复请求同一确认。课中发现新版本只提示，不静默换版本。

- 官方来源、安装仓库独立且干净：读取目标正式版更新日志，获取该 Release 的标签，核对标签版本后以 `git merge --ff-only <标签>` 快进到正式版（先 `git fetch origin tag <标签>`）。不直接跟随可能领先正式版的 main。若当前已领先目标、分叉、固定在其他版本或有冲突，停止自动合并并说明。
- 有本地修改、未跟踪文件或旧版无清单：先比对并保留备份；不能用 `reset --hard`、强制覆盖或删除来通过检查。确认这些差异是已纳入新版的旧改动后，可保留可恢复的备份／stash，再更新；其他差异需要保留和合并。
- 非 Git 安装：按同一正式标签的清单下载到新的暂存目录，先核对完整性，再比较并备份旧安装后替换；没有可靠替换能力时提供具体操作说明，不能覆盖一半就称成功。
- 更新后重新检查版本、文件清单和相对引用，重新读取新版入口；必要时开新任务确认宿主加载。文件已更新与宿主已加载分别报告。学生项目及作品保持在项目目录，不随 Skill 更新迁移或删除。

检查器输出 `review_local_changes`、`source_mismatch`、`maintain_source_repository`、`repair_or_compare_first` 或 `manual_compare_required` 时，都需要先处理对应问题；返回码 0 仅表示检查完成，不代表允许直接更新。

每次正式版本必须有 [更新日志](../CHANGELOG.md)，维护者发布按 [发布约定](../RELEASING.md) 执行。
